# Stage 0, measurements 1 and 2: document VLM on CPU

**28 July 2026** · Two questions for which there were no reliable public
figures: is the third reading stage viable locally, and does constrained
decoding work with multimodal models?

## Set-up

| | |
|---|---|
| Model | `granite-docling-258M` Q8_0 (Apache-2.0, 169 MB + 98 MB mmproj) |
| Runtime | llama.cpp in a container, **CPU**, 4 threads, 8 GB memory |
| Corpus | 10 synthetic documents, three scan qualities |
| Comparison | the same images as [measurement 3](stage0-ocr-2026-07-28.md) |

---

## Measurement 1: is the third reading stage viable locally?

| Quality | dpi | Hits | s/page | tok/s | Loops |
|---|--:|--:|--:|--:|--:|
| clean | 300 | 49.5% | 11.7 | 39.8 | **3 of 10** |
| **medium** | **150** | **97.7%** | **13.6** | **57.2** | 0 of 10 |
| poor | 150 | 85.1% | 13.1 | 49.6 | 1 of 10 |

The raw JSON records the qualities under their original German names
`sauber`, `mittel` and `schlecht`.

**Answer: yes, but only just — and only at 150 dpi.**

The technical analysis estimated “several tens of seconds to minutes per
page” and cited a report of 300 s for the vision encoding alone. Measured,
it is **13.6 s** for a complete A4 page. That is clearly better than feared,
but far from interactive.

### More resolution makes it worse

The most striking finding. At 300 dpi the model breaks down:

- **3 of 10 documents run into repetition loops** — 4096 tokens until the
  cut-off, 43 s instead of 12 s.
- The other seven stop halfway down the page: 281–467 tokens instead of the
  ~750 a complete page needs. Hence the 49.5%.

At 150 dpi everything runs through smoothly: 714–811 tokens, no loop,
96.4–98.0%.

This is exactly the failure pattern the architecture decision had noted for
Qwen3-VL (“repetition loops on tables, confirmed by maintainers”) —
reproduced here for granite-docling, triggered by the image size. A cap on
output tokens plus loop detection is therefore not a precaution but a must.

In passing this confirms the OCR measurement: there, too, 150 dpi was faster
**and** equally accurate as 300 dpi. For both reading paths, higher
resolution gains nothing on these documents.

### Compared with classical OCR

| | Tesseract | granite-docling | Factor |
|---|--:|--:|--:|
| Hits (150 dpi, medium) | 98.9% | 97.7% | |
| Hits (150 dpi, poor) | 98.8% | 85.1% | |
| s/page | 0.48 | 13.6 | **28× slower** |

**For these documents the third reading stage does not pay off.** Tesseract
is more accurate, twenty-eight times faster and does not fall into loops.

This holds for **printed business documents** — the case Substrakt is built
for. Where a VLM could play to its strengths (handwriting, nested tables,
forms without lines), this corpus does not cover. The reading stage therefore
remains planned as a swappable module — but it does not become the default
escalation.

## Measurement 2: constrained decoding with multimodal models

The architecture decision recorded: “Architecturally nothing speaks against
it, but the official documentation does not mention it, and there are known
grammar bugs in the system. That would have to be verified before committing
to it.”

**It works.** And the result is a warning all the same.

| Check | Result |
|---|---|
| Valid JSON | **10 / 10** |
| Schema satisfied (all required fields) | **10 / 10** |
| **Values correct** | **23 / 40 — 57%** |
| Time | 0.9 s |

`response_format: {"type": "json_schema", …}` is accepted and enforced by
llama-server even with an mmproj loaded. The form is right in every single
case.

The values are not:

| Field | expected | returned |
|---|---|---|
| `gesamtbetrag` | 22.849,78 | **3.648,28 EUR** ← the VAT |
| `gesamtbetrag` | 25.705,78 | **DE145889472** ← the VAT ID |
| `gesamtbetrag` | 27.893,48 | **612,80** ← a line item |
| `gesamtbetrag` | 25.705,78 | **K-4704** ← the customer number |
| `ust_idnr` | DE145889472 | **UST-IdNr.:** ← the field label |

Field names and values are quoted as recorded: the schema of that run used
German keys (`gesamtbetrag` for the total amount, `ust_idnr` for the VAT ID;
`bench/vlm.py` now calls them `total_amount` and `vat_id`), and the amounts
are written as printed on the German documents.

Each of these values is schema-conforming, plausibly shaped and appeared
somewhere on the document. None is the one sought.

### What this means for the architecture

The provenance layer is thereby no longer a reasoned precaution but a
measured necessity. An extractor relying on constrained decoding would have
shipped **43% wrong values** here — without any warning signal, because
parsing and schema validation report success.

The three rules from the build prompt pass the test:

1. **Region extraction takes precedence.** A marked rectangle returns the
   value that stands there — not the one that sounds plausible.
2. **Every value needs a location.** Fuzzy matching against the word index
   would have placed `3.648,28` on the VAT line, not at the total amount —
   the contradiction would have become visible.
3. **Without a location, “unsupported”.** With `UST-IdNr.:` as the value,
   matching finds no fitting place, and the field goes to a person for review
   instead of silently into the result.

## Limitations

**Synthetic corpus.** Printed, clean documents. A VLM might do better than
here on handwriting, stamps or tables without lines — this corpus does not
measure that.

**One model.** `granite-docling-258M` is the smallest of the candidates.
PaddleOCR-VL (0.9B) and dots.ocr (1.7B) are larger and probably more
accurate, but correspondingly slower; neither exists as GGUF, and both would
need PyTorch, which is excluded for this project.

**Docker overhead.** The measurement ran in a container with `--cpus=4`. A
native build would be a few percent faster.

**The prompt is not optimised.** `Convert this page to docling.` is the
standard call. For the field extraction in measurement 2 a simple English
prompt was used — with more careful prompting and few-shot examples the 57%
would probably be higher. That does not change the basic finding: form and
truth are two different things.

## Reproducing

```bash
./scripts/fetch-models.sh                     # granite-docling GGUF + mmproj
docker run -d --name substrakt-vlm --cpus=4 --memory=8g \
  -v $PWD/models/vlm:/models:ro -p 18080:8080 \
  ghcr.io/ggml-org/llama.cpp:server \
  -m /models/granite-docling-258M-Q8_0.gguf \
  --mmproj /models/mmproj-granite-docling-258M-Q8_0.gguf \
  --host 0.0.0.0 --port 8080 --threads 4 --ctx-size 8192

cd sidecar && uv run python ../bench/vlm.py --write
```

The commands use today's flag; the run on 28 July 2026 used the former German
flag. Raw data: [`stage0-vlm-2026-07-28.json`](stage0-vlm-2026-07-28.json).
